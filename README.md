# 豆瓣档案同步（DoubanArchive）

把 Emby / Jellyfin 的播放进度同步到豆瓣「书影音档案」。

## 与同类插件的差异

| 能力 | 常见实现 | 本插件 |
| --- | --- | --- |
| 媒体识别 | 必须调用 TMDB，TMDB 超时即放弃同步 | 不依赖 TMDB，TMDB 不可用时照常同步 |
| 豆瓣 ID 获取 | 网页爬取 `douban.com/search`，易被反爬卡住线程 | 优先读取媒体服务器已刮削的 `ProviderIds.Douban`，其次使用 frodo API 搜索 |
| 事件处理 | 在 webhook 线程里直接发网络请求 | 交给宿主的延后任务队列，事件线程立即返回 |
| 失败处理 | 仅记录日志 | 写入失败队列，每 30 分钟自动重试，也支持命令 `/douban_retry` 手动触发 |
| 网络超时 | 部分请求未设置超时 | 所有外部请求显式超时（默认 15 秒） |

## 状态判定

判定时机：开播（`PlaybackStart`）先记一条「在看」；播完（`PlaybackStop` / `PlaybackPause`）
或手动标记已播放（`UserDataSaved` + `SaveReason=TogglePlayed`）时重新判定并升级状态。

- 电影：出现播完类事件，或播放进度 ≥ 90% → 「看过」（collect）。
- 剧集：优先读媒体服务器里该集的 `UserData.Played`，为真即「看过」，为假即「在看」；
- 读取不到已播放标记时，回退到「是否本季末集」判断，末集集号取自 `Shows/{id}/Episodes` 的真实集号；
- 仍取不到（正在更新的剧集、元数据缺失）→ 保守记为「在看」，不误标看完。

### v1.3.0 修复的问题

此前「看完一集没被识别」有三个叠加原因：

1. **事件白名单漏了播完事件**。宿主把媒体服务器的原始事件名透传过来，Emby 播完发的是
   `PlaybackStop`，而白名单里只有 `PlaybackStart` 和两个标记事件。等于插件只在你点下播放那一刻
   同步过一次，之后你什么时候看完的它完全不知道。
2. **Emby 的手动标记进不来**。`UserDataSaved` 的判断写死在 `channel == "jellyfin"` 分支里，
   Emby 手动点「标记为已播放」同样不会被处理。
3. **季集数取法不可靠**。原来读 `Shows/{id}/Seasons` 的 `ChildCount`，依赖刮削元数据；
   未刮削或元数据异常时返回 0，静默降级成「在看」且不打日志。现改为逐集遍历，与宿主判断
   剧集存在性的口径一致。

另外修正：正在更新的剧集里，用户播放的集号可能大于已收录的最大集号（如只更到 4 集却看了第 5 集），
这种情况按「在看」处理，不再按「≥ 最大集号」误判为末集。

### 实测确认（v3.1.2-1）

对实际档案做了核对，修复前的表现：

| 标题 | 类型 | 集数 | 修复前状态 | 说明 |
| --- | --- | --- | --- | --- |
| 征途 | 电视剧 | S1E28（共 28 集） | 在看 | 已看到末集却没升级 |
| 小猪佩奇 迷你剧 第一季 | 电视剧 | S1E7（共 7 集） | 在看 | 同一症状，交叉验证 |

豆瓣 ID 均已正确抓到（征途 subject_id=38192991），问题纯粹在状态判定环节。

### 顺带发现并修复：多实例读错服务器

宿主 webhook 事件的 `server_name` 字段**从未被赋值**（`emby.py` / `jellyfin.py` 都没有写入），
原实现只取「第一个可用实例」。在配置了多台媒体服务器的环境下会读错服务器。
v1.3.0 增加「媒体服务器」配置项，多实例时回退到第一个会打 warn 日志提示。

媒体库过滤同样调整：宿主 `get_librarys()` 走 `Users/{user}/Views`，
该接口只返回 `Id` / `Name` / `CollectionType`，**不含 Path**，
因此改为沿 `ParentId` 逐级上溯定位所属库，路径比对仅作兜底。

## 重扫档案（v1.4.0）

v1.3.0 之前的存量数据无法自动修正——插件当时只在开播那一拍同步过，
早已看完的条目状态会一直停在「在看」。重扫功能按媒体服务器的真实播放状态批量校正。

三种触发方式：

| 方式 | 操作 |
| --- | --- |
| 配置页 | 勾选「重扫档案」后保存（任务延迟 5 秒执行，结束后自动复位开关） |
| 远程命令 | 发送 `/douban_rescan` |
| API | `POST /api/v1/plugin/DoubanArchive/rescan`（同步执行，直接返回逐条结果） |

判定逻辑：按标题定位剧集 → 读该季所有集的 `UserData.Played` → **整季全部已播放**才标「看过」。

### 排查

`GET /api/v1/plugin/DoubanArchive/diagnose` 返回每个环节的实际读取结果，
不依赖 MP 日志就能定位问题：

| 字段 | 含义 |
| --- | --- |
| `series_id` | 搜到的剧集 ID，为空说明标题没匹配上 |
| `episodes_count` | 该季实际集数 |
| `played_true` / `played_false` | 已播放 / 未播放集数 |
| `unfinished` | 具体哪些集没看完 |
| `result` | 本条的处理结论 |

`POST /rescan` 的返回值里 `trace` 字段是同样结构，同时带豆瓣写入结果。

安全约束（避免误伤）：

- **只升级不降级**，已是「看过」的记录直接跳过，不会被改回「在看」；
- **电影不参与**（没有集号概念，靠播放事件判定更准）；
- 媒体服务器查不到的条目**原样保留**，不猜测；
- 豆瓣 cookie 为空时直接中止，不动任何数据；
- 每条都要成功写入豆瓣才更新本地档案，写入失败计入 `failed` 不改状态。

详情页会显示「看过 / 在看」分项统计，方便核对重扫效果。

## 配置项

| 配置项 | 说明 |
| --- | --- |
| 启用插件 | 总开关 |
| 仅自己可见 | 豆瓣条目是否设为私密 |
| 不标记第一集 | 打开后跳过每季第一集 |
| 媒体库用户名 | 逗号分隔，只有这些用户触发的事件才处理 |
| 媒体服务器 | 配了多个 Emby/Jellyfin 时必须指定，否则可能读到另一台服务器的数据（宿主 webhook 不带服务器名） |
| 同步的媒体库 | 多选，只同步选中媒体库的内容；不选表示全部。选项从媒体服务器实时读取 |
| 媒体路径排除关键词 | 命中关键词的路径不处理（与媒体库选择独立生效） |
| 豆瓣cookie | 留空时从 CookieCloud 获取 |
| 使用CookieCloud | 关闭后仅使用上方 cookie |
| 立即重试失败队列 | 保存后立即执行一次重试 |
| 显示月份数 / 每月最多显示 | 仪表盘展示数量控制 |
| 内联豆瓣图片（防盗链） | 豆瓣图片带本站 Referer 会返回 403，开启后由后端取回并内联（默认开启） |
| 最多内联图片数 | 内联图片缓存上限，默认 20 |

## 仪表盘

- 通过 `get_dashboard_meta()` 声明 key `archive`，组件名为「豆瓣档案」，宿主的组件列表里可正常识别。
- 按月（含年份）分组的时间线海报墙，`VTimelineItem` 置于 `VTimeline` 内，避免时间线渲染不出来。
- 海报优先取豆瓣官方竖版封面，取不到时用媒体服务器的图；两者都没有则显示片名文字占位，记录不会从墙上消失。
- 缺失的封面会在每 30 分钟的重试任务里自动补齐（单次最多 5 条）。
- **豆瓣图片防盗链处理**：`doubanio.com` 的图片在浏览器里直连会返回 403（无 Referer 返回 418，只有 `movie.douban.com` 的 Referer 才 200）。
  因此插件由后端带上豆瓣 Referer 取回图片，转成 data URI 内联后再交给前端，并把结果缓存到插件数据键 `images`，
  之后每次刷新直接命中缓存。单次渲染最多回源 8 张，避免仪表盘请求过慢。

## 数据来源

同步档案存储在插件数据（宿主插件数据服务）中，键为 `archive`，失败队列键为 `pending`。
插件不会修改媒体服务器中的任何数据。

图标 `icons/douban.png` 取自插件社区常见素材，仅用于识别插件。
